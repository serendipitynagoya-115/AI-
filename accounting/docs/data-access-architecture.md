# データ取得アーキテクチャ調査(Dropbox原本のセル単位取得について)

2026-09-10、守山店8月の検証作業をきっかけに、Dropbox上のExcel(日報)を「セル座標を保持した状態」でClaude Codeから取得・解析できるかを調査した記録です。今後、他店舗に展開する際や、完全自動化を検討する際の判断材料として残します。数値そのもの(売上等)は含みません。

## 調査結果:現時点では不可能

このセッションで利用できるDropbox連携(MCP)には19個のツールがありますが、いずれも「ファイルのバイナリ内容をそのまま安全に取得する」用途には使えないことを確認しました。

| ツール | できること | セル単位の取得に使えるか |
|---|---|---|
| `search` / `list_folder` / `get_file_metadata` | ファイル・フォルダの検索、一覧、メタデータ取得 | 不可(位置情報を持たない) |
| `fetch` | ファイルのテキスト抽出(最大5MiB) | **不可**。実地検証で、同一表内の行でもタブ区切りの列数が33列〜63列とばらつくことを確認済み(空欄セルが位置を保持されずに詰められるため)。セル座標・結合セル・数式・列位置を保持しない。 |
| `download_link` | ファイルの一時ダウンロードURL(有効期限60〜900秒)を発行 | **不可(このセッションからは)**。発行されたURLは `*.dl.dropboxusercontent.com` のようなDropboxのCDNドメインを指すが、このセッションの組織ネットワークポリシーにより、このドメインへのアウトバウンド接続がブロックされている(プロキシで403拒否・ログで確認済み)。 |
| `file_preview` | サムネイルプレビューの取得 | 不可(画像のみ、データ取得不可) |
| `create_file` / `create_folder` / `move` / `copy` / `delete` 等 | 書き込み・整理系操作 | 対象外(今回は読み取りのみを調査。使用していない) |

### 根本原因

Dropbox MCPの `download_link` は、ファイル内容そのものをMCP経由で返すのではなく、「このセッションが自分でHTTPリクエストして取得しに行くための署名付きURL」を返す設計です。取得の実行主体はDropbox側のサーバーではなく、**このセッション自身**になります。

一方、比較のためGoogle Drive MCPの `download_file_content` を(既にアクセス許可済みの「2026 売上現状」で)試したところ、ファイル内容(Base64エンコード)がMCP応答の中に直接含まれて返ってくることを確認しました。この場合、実際にGoogleのサーバーへ接続しているのはMCPサーバー側であり、このセッションが新たに外部ドメインへ接続する必要がありません。

つまり、**Dropboxは「取得の最後の一歩」をこのセッションのネットワーク環境に委ねる設計になっており、Google Driveは委ねない設計になっている**、という違いが根本原因です。今回のケースでは、その「最後の一歩」に必要なドメイン(`dl.dropboxusercontent.com`)が、このセッションの組織ネットワークポリシーで許可されていませんでした(プロキシの403は組織のポリシー拒否であり、回避や再試行は行っていません)。

## 不足している機能・権限(まとめ)

1. Dropbox MCP側に、ファイル内容をサーバー経由(Base64等)で直接返す機能がない(Google Driveの `download_file_content` に相当する機能がDropbox側には無い)。
2. このセッションの組織ネットワークポリシーで、Dropboxのダウンロード用ドメイン(`*.dropboxusercontent.com` 等)へのアウトバウンドアクセスが許可されていない。
3. Dropbox APIを直接(MCPを介さず)呼び出すための、スコープ限定のアクセストークンが、このセッションには発行・保存されていない(そもそも今回はGitへの認証情報保存も避けるべきという指示のもと、取得を試みていない)。

## 将来、6店舗を完全自動化するための選択肢

いずれも、まだ何も実装していません。方針を決めていただいた上で、次のステップとして構築します。

### 選択肢1(おすすめ): 日報をGoogle Drive側にも集約する

「2026 売上現状」「2026店舗収支」は既にGoogleスプレッドシートで運用されています。日報側(現在Dropboxのみ)も、Googleドライブに自動同期・複製する仕組みを用意すれば、Claude Codeは今回実証済みの方法(Google Driveのセル単位取得)でそのまま読み取れます。

- 実現方法の例:Dropbox公式のGoogle Drive連携、Zapier/Make.com等のノーコード同期ツール、または各店舗が日報を保存する際にGoogleドライブへも保存するよう運用を変更する、など。
- メリット:Claude Code側の追加開発が最小限(今回のセッションで動作確認済みの経路をそのまま使える)。組織のネットワークポリシーを変更する必要がない。
- デメリット:同期の仕組みを別途用意する必要がある(運用面・ツール選定は要検討)。

**2026-09-10 追記(検証済み):** オーナーが守山店8月の日報「①8月.xlsx」をGoogle Driveへ手動でコピーしたところ、`mcp__Google_Drive__download_file_content` でExcel原本(.xlsx)をバイナリのまま取得でき、`openpyxl`でセル座標・結合セル・数式・保存済み計算値を保持した状態で解析できることを実証しました(`accounting/docs/moriyama-sales-mapping.md` 参照)。ファイルサイズ約1.8MBのExcelを問題なく取得できています。ただし今回は**オーナーによる手動コピー**であり、自動同期の仕組みはまだありません。恒常的な自動化には、この手動コピーを自動化する仕組み(Dropbox公式連携、Zapier/Make.com等)が別途必要です。

### 選択肢2: 組織のネットワークポリシーでDropboxのダウンロードドメインを許可する

管理者に、Claude Codeのセッションから `*.dropboxusercontent.com`(またはDropbox APIドメイン `api.dropboxapi.com` / `content.dropboxapi.com`)へのアウトバウンドアクセスを許可してもらう方法です。

- メリット:許可されれば、既存のDropbox連携(`download_link`)がそのまま使える可能性が高い。
- デメリット:Claude Code側では変更できず、組織の判断が必要。セキュリティポリシー上、許可されない可能性もある。

### 選択肢3: Dropbox APIを使った専用の自動化ジョブをClaude Codeの外側に用意する

Claude Codeのセッションとは別に、Dropbox APIのアクセストークン(スコープ限定)を安全な場所(シークレットマネージャー等。**Gitには保存しない**)で管理する小さな自動化ジョブ(サーバーレス関数など)を用意し、そこで毎月ファイルをダウンロード→openpyxl等でセル単位に変換→CSVやJSON、またはGoogleスプレッドシートとして出力する方法です。Claude Codeは、その「変換済みの出力」だけを読み取ります。

- メリット:人間の手動ダウンロード運用を完全になくせる。将来的に最も自動化度が高い。
- デメリット:Claude Codeのセッション外に新しいインフラ(実行環境・認証情報の管理)を用意する必要があり、初期構築コストが最も高い。

## 結論(2026-09-10更新)

**Dropbox連携単体では、このセッションからExcel原本をセル座標付きで安全に取得する方法はありません。** 会計ロジック側の問題ではなく、データ取得経路(このセッションのネットワークポリシーとDropbox連携の設計)の問題であることを確認しました。403エラーを回避するような非正規な方法は使用していません。2026-09-11に`download_link`が発行する一時URLへの実際の接続を試行し、組織ポリシーによる403拒否を実機で再確認済みです(推測ではなく実測)。Dropbox APIを直接呼び出すための認証情報もこのセッションには存在しません。

**一方、オーナーがDropbox原本をGoogle Driveへ読み取り専用ミラーとしてコピーする方法(選択肢1)は、実際に動作することを検証済みです。** 現時点では手動コピーですが、毎月の運用としては成立します。完全自動化(人間の手動作業をゼロにする)には、選択肢2または3への発展が必要です。

**2026-09-11追記(コピー範囲の確定):** 当初、日報Excelが他ブックを外部参照していることから「参照先ファイルも含めたフォルダ丸ごとのミラーが必要ではないか」を懸念していましたが、`①8月.xlsx`の外部参照を実地調査した結果、監査に必要な値(商品・スタッフマスター、期首在庫)はいずれも**対象月のファイル自身に保存済みキャッシュ値として存在する**ことを確認しました。読み取り専用(保存・再計算・リンク更新なし)で監査する限り、外部参照先ファイル(`年間集計.xlsx`・前月ファイル)にアクセスできる必要はありません。したがって、**コピーする範囲は「店舗・年月ごとの単一ファイル」で足り、フォルダ丸ごとのミラーは不要**と結論づけました。詳細な調査結果と正式ルールは [`product-audit-spec.md`](./product-audit-spec.md) §6・§7を参照してください。

方針(選択肢1の運用を続ける/選択肢2・3へ発展させる)が決まり次第、具体的な実装に進めます。
