# Googleスプレッドシート書き込み機能 設計書(設計のみ・未実装)

**ステータス: 設計のみ。実装(コード)はまだ書いていません。実際の書き込みも行っていません。** 数値は含みません。

## 前提とする運用方針(2026-09-10 オーナー確定)

1. 売上集計の正本は日報とする。
2. 「2026 売上現状」は日報から作る管理用集計表とする。
3. 日報と「2026 売上現状」が不一致の場合、日報側を正として差分案を作る。
4. ただし分類が曖昧な場合は自動修正しない。
5. 合計金額は一致していて新規・既存の分類だけ違う場合は「分類差異」として要確認にする。
6. 金額自体が違う場合は「金額差異」として要確認にする。
7. 8/6(今回のテスト対象)は日報側の売上を正として扱う方針で設計する。
8. 8/8は合計売上は有効とするが、新規・既存分類は自動修正せず要確認とする。
9. 来店区分と売上区分が異なること自体は必ずしも異常としない(体験当日の回数券購入等)。金額計上は売上列(AC/AD/AF)を基準とする。
10. 書き込み前に必ず「現在値・書き込み予定値・差額・理由」を一覧化する。
11. 書き込みは承認後のみ実行する。
12. 差異があるセルは自動承認・自動修正しない。
13. 書き込み前に対象範囲をバックアップする。
14. 書き込み後に再読込し、書き込み予定値と実際の値が一致したか検算する。
15. 失敗時に復元できる設計にする。

2段階運用:「2026 売上現状」は日次・店舗単位で更新、「2026店舗収支」は月次確定後に更新する。

`accounting/scripts/run_moriyama.py`(読み取り専用)が出力する日別集計・照合結果(一致/分類差異/金額差異/データなし、区分要確認一覧)を、この設計の入力として使う。

---

## A.「2026 売上現状」への書き込み設計

### 対象・粒度

- 日次・店舗ブロック単位。対象セルは、店舗ブロック内の「新規」「既存」「物販」列(および「累計」列。累計が数式か実値かは未確認 — 下記「実装前の確認事項」参照)。
- 書き込み候補は日ごとに、以下のいずれかに分類する。

| 照合結果 | 新規/既存/物販/累計セルの扱い |
|---|---|
| 一致 | 差額なし。書き込み対象外。 |
| 金額差異(例: 8/6) | 曖昧な分類を含まない項目(例:物販・累計)のみ、日報側の値を書き込み候補にする。新規・既存側に差がなければそちらは対象外。 |
| 分類差異(例: 8/8) | 新規・既存の内訳は**書き込み候補にしない**(ルール4・8・12)。合計(累計)・物販がすでに一致している場合は、その日は書き込み対象なし。万一累計側にも差がある場合は、累計のみ「要確認」として提示し、自動では書き込まない。 |
| データなし(未入力) | 「2026 売上現状」に該当日の行自体が無い/空欄の場合の扱い(新規行として追加してよいか)は未確定。オーナー確認事項とする。 |

### 書き込み候補オブジェクトの設計(1セルにつき1レコード)

```
{
  "date": "2026-08-06",
  "store": "守山店",
  "column": "物販",             # 新規 / 既存 / 物販 / 累計
  "cell_ref": "<未確定。実際のセル番地は書き込み実行前にSheets側で再解決する>",
  "current_value": <書き込み直前に再読込した値>,
  "proposed_value": <日報側の再集計値(税抜)>,
  "diff": <proposed - current>,
  "source": "日報 ①8月.xlsx シート'6' AF54(物販・税別)",
  "classification": "金額差異",
  "action": "propose_write" | "hold_for_review",
  "reason": "顧客名欄が空欄の物販取引2件が売上現状側に未反映"
}
```

`action = "hold_for_review"` のレコードは、一覧には出すが書き込み対象からは常に除外する(分類差異の新規・既存内訳など)。

## B.「2026店舗収支」への書き込み設計

### 対象・粒度

- 月次確定後、店舗ごとのタブの対象月列に対して、施術売上・物販売上(店販)・物販売上合計・売上合計の行を更新する候補を作る。
- 「月次確定」の定義(案): 対象月の全日について、「2026 売上現状」との照合が「一致」または「金額差異(是正済み)」であり、「分類差異」が残っていても合計(累計)側に影響しないことをオーナーが確認済みであること。分類差異が残ったまま店舗収支を確定してよいかは要確認。

### 特記事項

- 現状、「2026店舗収支」の売上系行はすべて0円(未入力)であることを確認済み。これは「値が0」なのか「単に未入力」なのか区別できないため、**初回書き込みは通常の差分書き込みと同列に扱わず、オーナーに「これは初めての入力になります」と明示した上で個別に承認を得る。**
- 「施術売上」「物販売上」の定義が、日報側のどの集計(新規+既存 / 新規+既存+回数券利用等)に対応するかは未確定(下記「実装前の確認事項」)。

### 書き込み候補オブジェクトの設計

```
{
  "year_month": "2026-08",
  "store": "守山店",
  "row": "施術売上",              # 施術売上 / 物販売上(店販) / 物販売上合計 / 売上合計 のいずれか
  "column": "8月",
  "cell_ref": "<未確定>",
  "current_value": <書き込み直前に再読込した値。初回は0または空欄の想定>,
  "proposed_value": <日報側の月合計(税抜)>,
  "diff": <proposed - current>,
  "source": "日報8月分の月合計(新規+既存、または物販)",
  "is_first_entry": true,
  "reason": "月次確定後の初回入力"
}
```

## C. 承認フロー設計

1. `run_moriyama.py`(読み取り専用)を実行し、最新の照合結果を得る。
2. 「書き込み候補生成」ステップ(未実装)が、A・Bの書き込み候補オブジェクトの一覧を作り、`accounting/output/proposals/<year-month>/<store_id>_<target>_proposal.csv`(Git管理対象外)に出力する。この時点ではAPI呼び出しは一切行わない。
3. 候補一覧を、現在値・提案値・差額・理由付きでオーナーに提示し、明示的な承認を得る(ルール10・11)。承認は「この一覧(内容のハッシュ・生成日時)に対する承認」として記録し、内容が変わった一覧への使い回しは無効とする。
4. 分類差異として `hold_for_review` になっている項目は、承認対象に含めない(そもそも書き込み候補として提示しない)。
5. オーナーは一覧の中から、行(セル)単位で「承認」「保留」「却下」を選べる設計とする(一括承認のみに限定しない)。
6. **書き込み直前の再チェック:** 承認から実行までの間に対象セルが変更されている可能性があるため、実行直前に対象セルを再読込し、承認時点の`current_value`と一致するか確認する。一致しない場合はその書き込みを中止し、「承認後に対象セルが変更されたため中止」として報告する(自動的に新しい値で上書きしない)。

---

## D. バックアップ設計

1. 書き込み対象範囲(セル単位ではなく、対象日・対象店舗ブロック全体、または対象月・対象店舗タブ全体など、ある程度の余白を持たせた範囲)を、書き込み直前に読み取る。
2. 取得した値を `accounting/backups/<store_id>/<year_month>/<target_sheet>_<timestamp>.json`(Git管理対象外)に保存する。内容: スプレッドシートID、シート名、範囲、取得時の値、対応する承認済み提案のID・ハッシュ、取得日時。
3. バックアップの保存が成功したことを確認できるまで、書き込みには進まない(バックアップ失敗時は書き込み処理全体を中止する)。

---

## E. 書き込み後検算設計

1. 書き込み直後に、書き込んだのと同じ範囲を再読込する。
2. セルごとに、再読込した値と提案値(承認された`proposed_value`)を比較する。
3. 一致(誤差許容は金額系で1円未満)であれば「検算OK」、不一致であれば「検算NG」としてログに記録する。
4. バッチ内の一部セルが「検算NG」の場合、そのバッチ全体を未完了として扱い、残りのセルへの書き込みを継続しない(全体を止めて報告する)。

---

## F. エラー時の復元設計

1. 復元の元データは、D で取得したバックアップスナップショット。
2. 書き込み後検算(E)が失敗した場合、またはAPI呼び出し自体がエラーになった場合、バックアップスナップショットの値を同じ範囲に書き戻す(ロールバック)。
3. ロールバック後、対象範囲を再読込し、バックアップ取得時点の値と一致するかを確認する(ロールバックの検算)。
4. ロールバックの実行内容(対象セル、復元前後の値、理由、日時)を必ずログに残す。
5. **ロールバック自体が失敗した場合(最悪のケース):** 自動での再試行は行わない。エラー内容・バックアップファイルのパス・対象範囲を明示し、オーナーに手動での復元(バックアップの値をスプレッドシート上で手動貼り戻す)を依頼する。
6. 複数セルをまとめて書き込むバッチ処理では、実際に書き込みが成功したセルのみを個別に記録し(全セル一括ではなく1セルずつの成否を追跡)、ロールバックも実際に変更されたセルのみを対象にする(未変更のセルまで誤って触らない)。

## 実装前に確認・検証が必要な技術的事項

- **Google スプレッドシートへのセル単位書き込み手段が、現在接続されているMCPツールセットに無いことを確認済み(2026-09-10)。** Google Driveコネクタが提供するのは `update_file`(タイトル・親フォルダの変更のみ。セル内容は対象外)、`create_file`(新規ファイルの作成)、`copy_file`/`trash_file`/`share_file` などで、Sheetsの特定セル・特定範囲だけを更新するAPI(`spreadsheets.values.update` 相当)は無い。**書き込み機能を実装するには、Google Sheets APIへの書き込みアクセスを持つ別のMCP接続(またはそれに相当する手段)を用意する必要がある。** これが無い限り、本設計書のA・Bはロジック設計のみで実装に進めない。
- 「2026 売上現状」の「累計」列が数式(自動計算)か固定値かが未確認。数式であれば新規・既存・物販のみを書き込めばよいが、固定値であれば累計も個別に書き込む必要がある。
- 「2026店舗収支」の「施術売上」「物販売上」の定義(日報のどの集計値に対応するか)が未確定。
- 「2026 売上現状」に対象日の行自体が無い場合(新規行の追加が必要なケース)の扱いが未設計。
