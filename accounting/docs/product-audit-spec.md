# 物販監査仕様書(価格履歴ベース)

Serendipity-J の物販(商品販売)取引を、価格改定をまたいでも正しく監査するための正式ルールです。数値は含みません(具体的な金額は `accounting/output/` 配下のGit管理対象外領域を参照)。

## 背景・目的

商品価格・仕入原価は将来変更されることがある(例:2026-09-01付でドクターセレン(マグネシウム)の通常価格・仕入原価が改定される)。**現在の商品マスター価格だけを使って過去取引を監査すると、価格改定前の正常な取引が誤ってエラー判定されることがある。** これを防ぐため、物販監査は必ず「取引日時点で有効だった価格・原価」を使用する。

## 1. 価格履歴マスター(`accounting/config/global/product_price_history.yaml`)

商品マスターは「現在値だけ」を持つのではなく、価格・原価の履歴を商品ごとに管理する。各レコードは最低限、以下を持つ。

- 商品名
- 適用開始日・適用終了日(両端を含む)
- 通常販売価格(税込)・(税別)
- スタッフ販売価格(税込)(このファイル上では任意。無い場合は別ファイルの社割ルールを参照)
- 割引ルール(任意)
- 仕入原価(税抜)
- 税率・税区分
- 出典・備考

取引を監査する際は、**取引日が含まれる価格履歴レコードを自動選択する。** 現在の商品マスター価格と過去取引価格が違っていても、当時の有効価格と一致していれば正常とする。過去の日報を現在価格で再計算しない。原価も同様に、取引日時点で有効だった原価を使用する。価格改定日の前後では、旧レコード・新レコードを明確に分ける(終了日と開始日を1日ずつずらして重複させない)。

**価格履歴レコードが存在しない(商品名自体が無い、またはレコードはあるが取引日をカバーしていない)場合は、推測で価格を補わず「G. 価格履歴不足」として要確認にする。**

## 2. スタッフ価格(社割)履歴マスター(`accounting/config/global/staff_price_rules.yaml`)

社割価格についても、通常価格と同様に期間付きの履歴を持つ。商品ごとに、次のいずれかの方式で定義する。

- **明示価格方式:** 社割価格表に金額が明記されている商品は、その金額を基準に監査する。
- **割合方式:** 「40%OFF」のように割合だけが定義されている商品(例:化粧品・一部の物販カテゴリ)は、取引日時点で有効な通常販売価格 × 割引率で社割価格を計算する。

**割合方式の端数処理(四捨五入/切り捨て/切り上げ、税込・税別どちらの段階で丸めるか)は、実際の社割価格表・過去の日報実績を確認してから正式ルール化する。現時点では未確定のため推測で決めていない。** 未確定の間、割合方式で計算した金額と実際の取引額の比較は「A(正常)」を自動確定せず、「I. 要現場確認」として扱う。

該当するレコードが無い商品・期間は「G. 価格履歴不足」として扱う。

### 価格比較は「値引前・値引後の両方」を試す(2026-09-11確定)

日報の物販行には、実売価格(P列)とは別に値引額(T列)がある。実データを調査した結果、次の2通りの運用が混在していることを確認した。

- 多くの一般顧客の取引では、P列にそのまま通常価格が入力されており、T列は本監査の対象外の調整に使われている(P列で比較すべき)。
- 一部のスタッフ購入では、P列に通常価格を入力したうえで、社割差額をT列の値引として記録している(値引後の金額 = P列−T列で比較すべき)。

**どちらか一方だけで固定的に比較すると、もう一方の正常な運用を誤って不一致と判定してしまう。** そのため監査ロジックは、値引前(P列)・値引後(P列−T列)の両方を期待価格と比較し、どちらか一方が一致すればそれを採用する。売上金額(AF列)自体はどちらの場合も変更しない。

## 3. 監査ロジック

各物販取引について、以下を算出する。

- 購入者、購入者区分(一般顧客/スタッフ/不明)
- 商品名、数量、取引日
- 通常価格、スタッフ価格(該当する場合)、実売価格、値引額
- 税抜売上(日報の実売をそのまま使用。会計AI側で再計算しない)
- 仕入原価、粗利益、粗利率

### 購入者区分の判定

顧客名が、店舗の担当スタッフ名簿(日報`基本情報`シートの所属スタッフ一覧)のいずれかで始まる場合は「スタッフ」と判定する(顧客名にフリガナが直後に続く表記のため前方一致で判定する)。顧客名が空欄の場合は「不明」とする。それ以外は「一般顧客」とする。

来店区分(D列:新規/既存/物販)と売上区分が異なること自体は、必ずしも異常としない(例:体験当日に回数券を購入するなど正常なケースがある)。**金額計上は売上列(P・W・AF)を基準とし、区分ラベルだけで金額を動かさない。**

### 判定区分(A〜I)

| 区分 | 内容 |
|---|---|
| A | 正常。価格履歴と一致(許容誤差内)、原価も判明。 |
| B | 丸め差。価格履歴とのわずかな差額で、丸め誤差の可能性が高いもの。 |
| C | 価格不一致。一般顧客(または購入者不明)の実売価格が、取引日時点の通常価格と一致しない。 |
| D | スタッフ価格不一致。スタッフ購入の実売価格が、取引日時点の社割価格と一致しない。 |
| E | 商品マスター不一致。現在の商品マスターと価格履歴レコードの内容が食い違っている(データ品質上の警告)。 |
| F | 原価未登録。価格履歴レコードはあるが、仕入原価が登録されていない。 |
| G | 価格履歴不足。商品名はあるが、取引日をカバーする価格履歴(通常価格または社割価格)が無い。 |
| H | 商品不明。商品名が価格履歴マスターに存在しない(未登録商品、または商品名の表記ゆれ)。 |
| I | 要現場確認。上記のいずれにも機械的に確定できない、または端数処理ルール未確定の割合方式社割など。 |

**重要:** 異常があっても「不正」「改ざん」と自動判定しない。あくまで「規定価格・原価・入力内容との不一致」として抽出し、現場確認対象とする。

丸め差(B)の許容範囲は、実際の丸めルールが確認できるまでの暫定値(数円程度)。将来、正式な丸めルールが確認でき次第、この閾値をルールベースの判定に置き換える。

### 集計用の排他的分類(primary_bucket)

判定区分(A〜I)は「価格・原価が規定通りか」を表す軸であり、購入者区分(一般顧客/スタッフ/不明)とは別の軸である。この2つを区別せずに売上を足し合わせると、同じ取引が二重に数えられたり、逆に抜け落ちたりする(2026-09-11、守山8月の再監査で実際に発生した集計不整合の原因)。

このため、売上集計には必ず次の5分類(相互排他・合計が物販総売上と一致する)を使う。

1. 一般顧客
2. スタッフ
3. 購入者区分不明(顧客名が空欄等で購入者を特定できない)
4. 商品不明(商品名が価格履歴に無い、または「無」のまま)
5. その他(上記のいずれにも該当しない、想定外のケース。空であるべき)

判定の優先順位は「商品不明」を最優先とし(商品が特定できない取引は、購入者区分に関わらずまず商品不明に分類する)、次に購入者区分で振り分ける。

## 4. 利益計算ルール

1. 売上は日報の実売(税抜)を使用する。
2. 原価は取引日時点で有効な原価を使用する。
3. 売上 − 原価 = 粗利益。
4. 原価不明(F)の場合は利益を確定しない。
5. 商品不明(H)の場合も利益を確定しない。
6. 価格履歴不足(G)、要現場確認(I)の取引も、原価または区分そのものが未確定であるため利益は確定しない。
7. 上記以外(A・B・C・D、および価格履歴レコードはあるが内容食い違いのみのE)は、実売と判明している原価から利益を確定する。価格が規定と違っていても、原価・商品自体が判明していれば利益計算自体は可能なため。
8. 利益が未確定の取引は、売上は記録した上で、通常の粗利益集計とは別に一覧管理する。

## 5. 6店舗共通での利用について

このマスター・ロジックは、店舗名や商品名をハードコードしていない設計であり、`accounting/scripts/lib/product_audit.py`の監査ロジック自体は全店舗で共通のまま使える。設定ファイルの店舗間の分離については§22(設定ファイルの3階層構成)を参照。

2026-09-15、みよし店8月の監査で、商品マスター(`global/product_price_history.yaml`)・社割ルール(`global/staff_price_rules.yaml`)が守山店と完全に同一の内容(商品名・価格・原価・社割ルールいずれも一致)であることを確認した。したがって、この2つは店舗ごとに個別管理するのではなく、**全店舗共通のglobal設定として1つにまとめる。** 担当スタッフ名簿は店舗ごとに異なる(日報`基本情報`シートから店舗ごとに取得する。ハードコードしない)。

- 商品マスター(価格・原価履歴)・社割ルールは全店舗共通(global)。ただし、実際に他店舗でも同一であることは、その店舗のデータで確認できてから確定させる(推測で他店舗にも同一と決めつけない)。
- 担当スタッフ名簿は店舗ごとに異なるため、購入者区分の判定に使うスタッフ名リストは店舗ごとの日報`基本情報`シートから都度取得する(ハードコードしない)。
- 端数処理ルールは、確認でき次第、全店共通のルールとして `accounting/docs/product-audit-spec.md`(本ファイル)に明文化する。

## 6. データ鮮度チェック(正式ルール・2026-09-11確定)

物販監査(および売上集計・照合スクリプト)は、Dropbox原本そのものではなく、**「月次Excel単体の監査用コピー」**(Google Driveミラー等、`data-access-architecture.md` で確認済みの経路で取得したもの)を読み取る。このコピーは、コピーされた時点のスナップショットであり、Dropbox原本がその後も更新され続けている限り、時間の経過とともに古くなる。

2026-09-11、守山8月の再監査で、当時のミラー(`accounting/data/moriyama/2026-08/①8月.xlsx`)を元にした集計結果が、オーナーが確認した「現在の」月報集計の数値と大きく乖離する事象が発生した。Dropbox原本のメタデータを確認したところ、原本のファイルサイズ(1,817,637バイト)とミラーのファイルサイズ(1,793,918バイト)が異なり、原本はその後も更新され続けていることを確認した。**これは監査ロジックの不具合ではなく、入力ファイルの鮮度の問題である。** この事象を踏まえ、以下を毎回・例外なく実行する正式な鮮度チェック手順として確定する。

### 監査開始前の鮮度チェック手順

監査(または売上集計・照合)を開始する前に、必ず以下を確認する。一致しない場合は**監査を開始せず停止し**、「最新ファイルではない」と報告する。

1. **Dropbox原本側**の次の情報を取得する(`get_file_metadata`)。
   - ファイル名
   - ファイルサイズ
   - 更新日時(`server_modified`)
2. **監査用コピー側**の次の情報を取得する。
   - ファイル名
   - ファイルサイズ
   - 更新日時
   - SHA-256(コピー取得後に算出)
3. Dropbox原本と監査用コピーの**ファイル名・ファイルサイズ**を突き合わせる。一致しない場合は、新しい監査用コピーを取得し直すまで先へ進まない。
4. 補助チェックとして、監査用コピーを開き、`月報集計`シートの主要合計値(実売合計・内物販等)を読み取り、オーナーが把握している「現在の」値と概ね一致するかを確認する。これはファイルサイズ・更新日時の一致確認を補強するものであり、これだけで鮮度を確定してはならない(サイズ・更新日時の一致が主判定基準)。
5. 上記いずれかが不一致の場合、監査結果を「確定」として報告しない。

**守山8月の参考値(2026-09-11時点でオーナーが確認した現在値):**

- 月報集計・実売合計:約 2,209,818.21円
- 月報集計・内物販:約 772,881.85円

この値は補助チェック(上記手順4)にのみ使用し、ファイルサイズ・更新日時・SHA-256による一致確認を代替するものではない。

## 7. 外部参照ファイルの取扱い(読み取り専用監査における結論・2026-09-11確定)

守山8月の日報Excel(`①8月.xlsx`)には、他ブックへの外部参照(`年間集計.xlsx`の商品・スタッフマスター、前月ファイル`①7月.xlsx`の期首在庫)が実在することを、ファイル内部のXML(`externalLinks`)・全シートの数式・`definedNames`を直接調査して確認した。調査の詳細と結論は次の通り。

### 確定事項

- **外部参照は存在する。** ただし範囲は限定的で、`基本情報`シート(商品・スタッフ・媒体マスター、`年間集計.xlsx`参照)と`在庫帳`シートのF列(期首在庫、前月ファイル参照)のみ。日別シート(`1`〜`31`)・`月報集計`シートには外部参照が一切ない。
- **会計AI監査に必要な値は、月次ファイル単体の保存済みキャッシュ値から取得可能。** 外部参照セルであっても、最後に保存された時点の計算結果(キャッシュ値)がxlsx内部に保存されており、実測で商品価格・原価・期首在庫のキャッシュ値が既存マスター(`product_price_history.yaml`等)と一致することを確認済み。
- **Excelの再計算・外部リンク更新・再保存は不要。** 読み取り専用でキャッシュ値を読むだけであれば、外部参照先ファイル(`年間集計.xlsx`・`①7月.xlsx`)にアクセスできなくても監査は成立する。
- **したがって監査用途では、月次ファイル単体で処理可能。** フォルダ全体(参照先ファイルを含む)を丸ごとミラーする必要はない。

### 外部参照は「編集用依存関係」であり「読み取り監査用依存関係」ではない

外部参照が存在するという事実は、「このExcelを開いて正常に再計算・編集するために必要な依存関係」を示すものであり、「保存済みの値を読み取り監査するために必要な依存関係」を示すものではない。この2つを混同し、外部参照の存在だけを理由に「単体では監査不可」と判断してはならない。監査に必要なのは後者(読み取り)のみである。

### Excelファイルの取扱いルール(正式ルール)

1. Excelは読み取り専用で扱う。
2. 保存しない。
3. 再計算しない。
4. 外部リンクを更新しない。
5. `data_only=True`相当の保存済み値(キャッシュ値)を監査に使用する。
6. `formula`モード(`data_only=False`)は、数式構造・参照関係の確認用としてのみ使用し、監査の集計値には使用しない。
7. 外部参照先ファイルが存在しない・アクセスできない状態(リンク切れ)であっても、それだけを理由に監査不可と判断しない(キャッシュ値が読めれば監査を継続する)。
8. 保存済みの値が欠落しているセル(キャッシュが無い、または空)は、推測で埋めず「未確認」として扱う。
9. 数式エラー(`#REF!`・`#N/A`等)やキャッシュ欠落を検知した場合は、処理を完了扱いにせず「要確認」として報告する。

### 基本構成(2026-09-11確定)

```
Dropbox原本
  ↓
月次Excel単体の監査用コピー(店舗・年月ごとに1ファイル。フォルダ丸ごとのミラーは不要)
  ↓
Claude Codeによる読み取り専用解析(data_only相当のキャッシュ値を使用)
```

参考:調査で確認した外部参照の内訳は次の通り(値は含まない)。

| 参照元シート | 参照先ブック | 参照先シート | 用途 | 監査への必要性 |
|---|---|---|---|---|
| `基本情報`(ほぼ全域) | `年間集計.xlsx` | `コース等マスター` | 商品・スタッフ・媒体マスターの取り込み | キャッシュ値で代替可(推奨:単体コピーのままでよい) |
| `在庫帳`(F列のみ) | `①7月.xlsx`(前月ファイル) | `在庫帳` | 期首在庫(前月末在庫)の引き継ぎ | キャッシュ値で代替可(推奨:単体コピーのままでよい) |

## 8. 商品マスターの「現在値」と価格履歴の優先順位(2026-09-12確定)

守山8月のマグネシウム(ドクターセレン)監査で、次の事象が確認された。

- 2026-09-10以降にDropboxから再取得した`①8月.xlsx`では、`基本情報`シートのマグネシウムの表示価格が、8月分のファイルであるにもかかわらず、既に2026-09-01以降の新価格(税込3,672円/税抜3,400円)へ更新されていた。
- 8月中の実際の販売取引17件も、値引前金額(P列)が例外なく3,672円で記録されていた。
- しかし2026-09-12にオーナーへ確認した結果、2026-08-31までは旧価格(税込3,456円/税抜3,200円)が正式に確定した価格であり、`①8月.xlsx`内の「現在の」表示価格3,672円は、9月への商品マスター更新後の状態であって、8月当時の価格の証拠として使用してはならないことが明示された。

**この事象から、以下を正式ルールとして確定する。**

1. **価格監査の判定は、必ず取引日を基準に`product_price_history.yaml`の有効期間(`effective_start_date`〜`effective_end_date`)から行う。** 日報Excel(`基本情報`シート等)の「現在の」表示値は、価格履歴マスターを新規作成・更新する際の情報源にはなり得るが、**既に確定している過去の期間の価格履歴レコードを、日報Excelの現在値だけを理由に書き換えてはならない。**
2. **商品マスターは月次ファイルの保存後も更新され続ける(過去分を含めて表示が変わる)ことがある。** ある月のExcelファイルを取得したタイミングによって、そのファイル内の「現在の」商品マスター値が、実際にその月に適用されていた価格と異なる場合がある。これは監査対象の日報Excel自体の仕様であり、監査ロジックの不具合ではない。
3. **監査エンジン(`accounting/scripts/lib/product_audit.py`)は、取引の価格判定に`基本情報`シートの値を直接参照せず、`product_price_history.yaml`(取引日で選択される期間付きレコード)のみを使用する設計になっている。** `基本情報`シートは、購入者区分の判定に使うスタッフ名簿の取得にのみ使用し、価格・原価の判定には使用しない。この設計により、日報Excelの「現在の」表示値が過去の価格判定に混入することはない。
4. **価格改定が判明した場合、既存の期間のレコードを書き換えるのではなく、新しい`effective_start_date`を持つ別レコードを追加する。** 例:マグネシウムは2026-08-01〜2026-08-31の旧価格レコードと、2026-09-01始期(終期未定)の新価格レコードを別々に保持する。
5. **価格改定前後で、日報Excelの現在値と過去の価格履歴レコードが一致しないこと自体は異常ではない。** 過去の取引の実売価格が、取引日時点で有効だった価格履歴レコードと一致しない場合は、まず通常通り「C:通常価格不一致」「D:スタッフ価格不一致」と判定する。そのうえで、実売価格が**別の期間**の価格履歴レコード(例:直後の月の新価格)と一致する場合に限り、「K:既知差異」に区分し直す(§9参照)。現在の表示値と一致することだけを理由に、機械的に「正常」へ変更することはしない。

## 9. 価格監査と原価監査の分離、既知差異(K)区分、購入者別名(alias)(2026-09-13確定)

### 価格監査(A軸)と原価監査(B軸)の分離

物販監査は、次の2つの軸を独立して管理する。一方が未確定でも、他方の確定を妨げない。

- **A. 価格監査:** 実売価格が取引日時点の規定価格と一致するか。状態は「価格確定」「価格要確認」「既知差異」の3つ。
- **B. 原価監査:** 仕入原価(`cost_price_excl_tax`)が価格履歴マスターに登録されているか。状態は「原価確定」「原価未確定」の2つ。

**スタッフ社割価格の履歴が未登録(価格監査上は要確認)であっても、商品自体の原価が価格履歴に登録されていれば、原価監査上は原価確定として扱い、売上原価・粗利益の集計に含める。** 2026-09-12の守山8月監査で、この2軸を分離せず「価格が確認できない取引は原価も含めて全て未確定」と一体で扱っていたため、在庫帳ベースの売上原価(447,287.20円)と監査エンジンの確定売上原価(443,287.20円)の間に4,000円の差異が生じた(原因はスタッフ購入1件・コントアBクリームで、社割価格未登録により原価まで除外されていたこと)。この事象を踏まえ、2軸を分離する設計へ改めた。

### 既知差異(K)区分

価格不一致(C・D)と判定された取引について、実売価格(値引前・P列)が、取引日時点以外の期間の価格履歴レコードの通常価格と一致する場合、「K:既知差異」に区分し直す。これは、日報Excelの商品マスターが後日更新され、過去の取引行の表示価格まで変わってしまう事象(§8)が原因であると特定済みのケースを、原因未特定の価格不一致と区別するためのものである。

- 既知差異(K)は、重大度としても「既知差異」という独立した区分とし、「正常」「注意」「要確認」「重大エラー」のいずれにも含めない。
- 既知差異と判定された取引には、異常値引き等の追加フラグは付与しない(原因が価格差異そのものであるため、二重に要確認として扱わない)。
- 既知差異であっても、実売価格そのものが変わるわけではないため、原価監査・粗利益計算には通常通り含める。

### 購入者別名(staff_aliases.yaml)

日報の「購入者」欄が、担当スタッフ名簿(基本情報シート)と完全一致しない表記(ひらがな表記、旧姓、オーナーの通称等)で記録され、購入者区分が誤って「一般顧客」「購入者不明」になるケースがある。`accounting/config/stores/{store_id}/staff_aliases.yaml`に、別名(alias)と正式氏名(formal_name)の対応をオーナー確認済みのものだけ登録し、購入者区分の判定(`classify_purchaser`)で別名一致も反映する。別名解決後の正式氏名が担当スタッフ名簿に該当すれば「スタッフ」、該当しなければ「社内購入」とする(§10参照)。推測で別名を追加しない。

## 10. 購入者区分・商品特定状態の分離、管理会計上の物販粗利益(2026-09-14確定)

### 購入者区分(4分類)と商品特定状態(2分類)は独立した別軸

2026-09-11時点では「購入者区分」と「商品が価格履歴にあるか」を1つの排他的な集計バケット(`primary_bucket`、5分類)にまとめていたが、これだと商品不明の取引が購入者区分別の集計から機械的に除外され、「一般顧客なのに商品が特定できない」といった実態を表現できなかった。2026-09-14、次の2軸に分離した。

- **購入者区分(4分類・排他的・合計が物販総売上と一致):** スタッフ/社内購入/一般顧客/購入者不明
- **商品特定状態(2分類・排他的・合計が物販総売上と一致):** 商品特定済み/商品不明

1つの取引は、両方の属性(例:購入者=一般顧客、商品=商品不明)を同時に持つ。商品不明であることを理由に購入者区分の集計から除外したり、逆に商品特定状態を理由に購入者区分を確定させたりしない。

### 管理会計上の物販粗利益

物販監査には、目的の異なる2つの粗利益指標がある。名称を混同しないこと。

- **管理会計上の物販粗利益(正式):** `物販売上総額 − 実績売上原価`。価格監査(通常価格/社割価格が規定通りか)や商品特定状態の未確定があっても、売上自体を管理会計の売上から除外しない。売上原価には、原価監査(§9)で「原価確定」と判定された全取引の原価を実績原価として使用する。守山8月では、在庫帳当月販売金額・日別数量×原価・在庫増減式の3方式が一致する447,287.20円を実績原価として使用する。
- **商品特定済み粗利益(別名:監査確認済み粗利益):** 商品特定済み・原価確定の取引範囲のみに限定した粗利益。監査で個別に確認が取れた範囲を示す診断用の指標であり、管理会計上の物販粗利益の代わりに経営判断へ使ってはならない。

商品不明・価格要確認の取引であっても、実売(AF列)に計上された売上自体は必ず管理会計上の物販売上総額に含める。不明なのは「原価の内訳」や「価格が規定通りか」であって、売上そのものではない(`accounting/CLAUDE.md`最重要ルールと同じ考え方)。

## 11. 売上シェア(1商品を複数スタッフで分担入力)(2026-09-15確定)

### 業務ルール

1つの商品を、2名または3名のスタッフが一緒にお客様対応した場合、その商品の売上実績をスタッフの人数で分担して入力する運用がある(オーナー確認済み)。例(プロテイン、通常価格5,940円、1個販売):

- スタッフA: 商品名「プロテイン」、売上2,970円
- スタッフB: 商品名「無」、売上2,970円

この場合、実際の商品販売数量は1個、実売上は5,940円であり、2,970円への値引販売でも、「無」側の2,970円が別の商品の売上でも、重複売上でもない。単に、2人(または3人)のスタッフに売上実績を分担して記録するための入力である。

### 検出根拠の優先順位

自動判定で「無」行をすべて売上シェア扱いにしてはならない。判定は次の優先順位で行う(`detect_and_apply_shared_sales`)。

1. **日報I列の明示記載を最優先の一次証跡とする。** I列は単純な「備考」欄ではなく、「既存 単発・回数券」(施術チケットの種別)を記録する欄である(§13参照)。ただし特殊運用として、その欄に「売上シェア」という文字列が入力される場合があり、守山8月の実データで、シェア分担側の「無」行にI列「売上シェア」という明示記載があることを確認済み(店舗側の運用として、シェア入力であることを自ら記録している)。この記載がある場合、金額の一致・近接行等の推測より優先してシェア判定の根拠とする(`SHARE_MARKER_LABEL = "売上シェア"`、`_has_share_marker`)。I列自体の意味を「売上シェア専用欄」と再定義するものではない。
2. I列に明示記載がある「無」行(1〜2行)について、商品名が記録された行(実売価格が規定価格に届かない、classification=C)と、**「商品あり行の金額 + 無行の金額(1〜2行の合計) = 取引日時点の規定価格 × 数量」が一致するか**を確認する(この金額一致自体が2つ目の重要な判定根拠)。一致すれば、2名・3名いずれも確定した業務ルールとして扱い、classification等を正常化する。候補が複数あり一意に決まらない(曖昧な)場合は確定しない。
3. **I列に明示記載が無い「無」行**については、同日・近接行・金額の一致のみを根拠に「シェア候補(未確定)」として情報を付与するのみとし、classification・severity・原価・数量は変更しない(推測だけでは自動確定しない)。
4. I列に明示記載があるのに、対応する商品あり行を日報上で特定できなかった行(例:2026-08-17の6,210円、対応する商品行が見当たらないケース)は、`transaction_type="unknown"`とし、要確認フラグを追加するのみで、classification・severityは変更しない(自動で正常化しない)。

I列の読み取りは店舗・月を問わず共通の仕組みとして実装しており(`run_product_audit.py`の`extract_retail_rows`がI列の生値を取得し`share_marker_raw`として保持)、他店舗・他月の日報でも同様の記載があれば同じロジックで一次証跡として扱う。記載が無い日報では単に判定に影響しない。

### 確定した場合の監査上の扱い

売上シェアとして確定(`transaction_type="shared_sale"`)した取引は、以下のとおり扱う。

- classificationは「S(売上シェア確定)」とし、価格異常(C・D等)にも商品不明(H)にも、重複売上にもしない。severityは「正常」とする。
- 物販売上総額(各行のtax_excl_revenue)は変更しない。各スタッフの売上実績(購入者区分別集計)も、シェアされた金額をそのまま保持する(合算や付け替えをしない)。
- 商品原価は、「商品あり」側の行1個分だけを実際の売上原価として扱う。「無」側の行は`cost_excl_tax_total=0`・`cost_confirmed=True`とし、原価を二重計上しない。
- 商品販売数量は、「商品あり」側の行の数量のみを計上する。「無」側の行は`quantity=0`とし、数量を二重計上しない。
- 「無」側の行も`product_status="商品特定済み"`とする(シェア分担入力と判明しているため)。
- 「無」側の行の`gross_profit`は、原価0円のためその行の売上(tax_excl_revenue)がそのまま粗利益になる(`gross_margin=1.0`)。

3名で分担する場合(例:2026-08-01のルイボスティーPONO、792円×3行=規定価格2,376円)も、I列の明示記載と金額一致の両方が確認できれば、2名の場合と同様に確定した業務ルールとして扱う。I列の記載が無く金額の一致のみで3名以上への分担が疑われる場合は、実際にそのような運用が行われるか未確認のため、「シェア候補」のまま確定しない。

### スキーマ

`ProductTransaction`に以下のフィールドを保持する(既存の判定区分・重大度・原価監査等の設計とは独立)。

| フィールド | 内容 |
| --- | --- |
| `transaction_type` | `normal_sale` / `shared_sale` / `shared_sale_candidate` / `unknown` |
| `share_group_id` | シェアグループの識別子(日付・行番号から生成) |
| `share_count` | グループ内の行数(2名なら2、3名なら3) |
| `share_total` | グループ全体の合計金額(規定価格×数量と一致する額) |
| `linked_product` | グループが表す実際の商品名 |
| `linked_rows` | グループを構成する全行番号 |
| `share_marker_raw` | 日報I列(既存 単発・回数券欄)の生値。「売上シェア」の明示記載を保持する一次証跡 |

出力は`{store_id}_shared_sales.csv`(グループ単位のサマリ)と、`{store_id}_product_audit_detail.csv`の該当列(取引単位の明細、`share_marker_raw`含む)に反映する。元Excelへの書き込みは行わない。

## 12. 顧客名空欄=同一購入者の連続購入ブロック(2026-09-15確定)

### 業務ルール

守山の日報では、同じ人が複数商品をまとめて購入した場合、最初の商品行だけ顧客名(B列)を入力し、その後に続く同一購入者の商品行は顧客名を空欄にして入力する運用がある。したがって、**「顧客名が空欄=購入者不明」とは限らない。**

### 確定方法(推測で全件に適用しない)

この慣習が実際にどの範囲まで適用されているかを機械的に断定するのはリスクが高い(空欄=本当に購入者不明な一見客のケースも多数ある)。このため、`accounting/config/stores/{store_id}/{year_month}/confirmed_purchaser_blocks.yaml`に、**オーナーが日報原本を確認して確定した範囲だけ**を明示登録する(`store_id`・`year_month`・`date`・`start_row`・`end_row`・`purchaser_name`)。範囲外の空欄行は、従来通り「購入者不明」のまま扱う。

`apply_confirmed_purchaser_blocks`(`product_audit.py`)が、登録済み範囲内で顧客名が空欄の行にだけ起点行の購入者名を適用する(既に顧客名が入力されている行は上書きしない)。適用した行には、`purchaser_name_note`に適用根拠を記録する。

顧客名が確定すれば、以降は通常の購入者区分判定(`classify_purchaser`・別名マスター)がそのまま働く。スタッフ名簿に該当すれば「スタッフ」、別名マスターで社内購入者と確定していれば「社内購入」として扱う。

### 守山8月で確定した範囲

守山8月については、次の連続購入ブロックを確定した(詳細は`confirmed_purchaser_blocks.yaml`)。

- 8/5: 辻明子(社内購入者。`staff_aliases.yaml`に登録)
- 8/10: 小川麻菜、ひらたえりか(平田絵里可)、おぜきりか(尾関リカ)
- 8/11: こたぎりけいこ(小田切敬子)
- 8/27: 小川麻菜、西原ゆかり、おぜきりか(尾関リカ)
- 8/31: 澄川真

これにより、従来「一般顧客/購入者不明だが実売価格が社割(スタッフ)価格と一致」として要確認になっていた取引の多くが、実際には該当ブロックの購入者(スタッフ本人または社内購入者)による通常価格・社割価格どおりの正常な購入だったことが確定した。

### 副作用(新たに判明する項目)への対応方針

顧客名を正しく適用した結果、購入者区分が「一般顧客/不明」から「スタッフ」に変わり、比較対象が通常価格から社割価格に切り替わることで、**それまで隠れていた別の要確認事項(該当商品の社割ルール未登録等)が新たに表面化することがある。** これは監査ロジックの誤りではなく、より正確な購入者情報に基づいた結果であるため、隠さずそのまま出力する(推測で正常扱いにしない)。

## 13. I列の正しい定義(2026-09-15確定・訂正)

**I列は単純な「備考」欄ではない。** 日報上のI列は「既存 単発・回数券」(施術チケットの種別・回数券名)を記録する欄であり、物販専用の欄でもない。以前(§11初版)、この列を「備考」と表現していたが、2026-09-15にオーナーが日報原本を確認し、誤りと判明したため訂正する。

ただし、特殊運用として、この欄に「売上シェア」という文字列が入力される場合があることが確認されている。§11の売上シェア自動判定は、この「売上シェア」という**文字列そのもの**を一次証跡として利用するものであり、I列自体の意味を「売上シェア専用欄」と再定義するものではない。コード・コメント上でも、I列を「備考」と表記しないこと。

## 14. 物販監査対象からの区分振替(2026-09-15確定)

> **訂正(2026-09-15、§21参照):** 本節が実例として挙げていた守山8月・8/17行8(6,210円)の
> 区分振替は、スタッフ回答の再確認により誤りと判明し、撤回した。行8は施術売上ではなく、
> 行6・行7を含む売上シェアグループの一部である。この仕組み(区分振替)自体は他の
> ケースで引き続き有効だが、8/17行8への適用は取り消し済み。詳細は§21を参照。

### 背景

物販監査(`extract_retail_rows`)は、日報の日別シートでK列(数量)・P列(値引前金額)のいずれかが入力されている行を、機械的に「物販の取引行」として抽出する。しかし、D・F・I列(既存/回数券欄)の記載から、実際には施術・回数券(既存)側の売上であって物販の商品購入ではないと判明する行が存在しうる場合に、この仕組みを使う。

### 確定方法

`accounting/config/stores/{store_id}/{year_month}/confirmed_category_reclassifications.yaml`に、オーナーが日報原本を確認して確定した行(`store_id`・`year_month`・`date`・`row`・`tax_excl_revenue`・`reclassified_as`・`reason`)だけを明示登録する。登録された行は、物販監査(売上・原価・数量集計、価格・商品不明判定、売上シェア判定のいずれも)から完全に除外し、`{store_id}_category_reclassifications.csv`に施術/既存側への振替として出力する。原価はこの行に付けない(物販の商品原価としては扱わない)。

### AF54突合への影響

日別シートのAF54は`=SUMIF(AF4:AF53,">0")`であり、D列(新規/既存/物販)を区別しない単純合計である。したがって、区分振替で物販監査から除外した行の分だけ、監査エンジン側の物販合計はAF54より小さくなる。この既知の差額(振替額)を戻して比較することで、突合を継続する(`engine_sum + reclassified_total` と `AF54` を比較する)。全体の入金額そのものは変わらない。

## 15. 分類保留ステータス(2026-09-15確定)

事実関係(購入者・原価等)はオーナー確認により確定しているが、価格履歴・社割ルールマスターへの正式登録がまだ済んでいないため、classificationを「A(正常)」に確定できない取引がある(例:守山8月8/11のコントアBクリーム。小川麻菜本人のスタッフ購入と確定済みだが、40%OFF相当の値引が正式な社割ルールとしてマスター登録されるかは未確定)。

このような取引は、`accounting/config/stores/{store_id}/{year_month}/confirmed_status_overrides.yaml`に明示登録し、`apply_confirmed_status_overrides`によりseverityのみ「分類保留」に変更する。classification(価格・原価判定の区分)自体は変更しない(推測で価格・原価を確定しない)。「分類保留」は「正常」「既知差異」と同様、要確認一覧・重大エラーには含めない。

推測で追加せず、オーナーが日報原本を確認して確定した行だけを登録すること。対象商品を特定の社割ルール(例:○%OFF)としてマスター登録するかどうかは、このステータス上書きとは別に、マスターデータ整備の判断として行う(自動では確定しない)。

## 16. 社割価格の確定済み丸め差(2026-09-15確定)

### 背景

社割(スタッフ)価格が「税込通常価格×割引率」で決まる商品は、計算結果が小数(銭単位)になることがある。この場合、「値引額を丸める」か「最終価格を丸める」かで、正式に登録されているスタッフ価格(`explicit_staff_price_incl_tax`)と実際の取引額の間に1円程度の差が生じうる。

例(守山8月8/27・アガベシロップ):通常価格1,026円×20%OFF=820.8円。値引額(206円)を丸めた場合の実売は820円だが、正式なスタッフ価格は821円(最終価格を丸めた値)として登録されている。この1円差は、価格に異常があるわけではなく、円未満の端数処理方法の違いによるものとオーナーが確認・確定した。

### 適用方法(商品ごとに明示登録)

この丸め差は商品・社割ルールごとに事情が異なりうるため、全商品に一律の許容範囲を広げるのではなく、`accounting/config/global/staff_price_rules.yaml`の該当レコードに`confirmed_rounding_tolerance_yen`(円)を明示登録した商品にだけ適用する。登録されたレコードについては、実売価格(値引前・値引後いずれか)と正式なスタッフ価格の差がこの許容範囲内であれば、「B(丸め差の可能性・注意)」ではなく「A(正常)」として扱う。正式なスタッフ価格(登録値)を優先して使用し、割引率から都度再計算しない。

推測で全商品・全パーセンテージに適用せず、オーナーが商品ごとに確認・確定したものだけを登録すること。`confirmed_rounding_tolerance_yen`が無い商品は、従来通り`ROUNDING_TOLERANCE_YEN`(暫定許容範囲)に基づく「B(注意)」のまま扱う。

## 17. 店舗全体売上・物販売上・施術/既存売上の区別(2026-09-15確定)

### 用語の誤解を避けるための整理

物販監査(本ドキュメント・`run_product_audit.py`)が扱う金額(例:772,881.85円)は、**あくまで「物販売上」であり、店舗全体の売上ではない。** 「全体売上」という表現を物販売上に対して使わないこと。

守山8月の店舗全体の実売合計(月報集計シート「実売（実績）」の累計)は約2,209,818.21円であり、これは「内回数券等(施術・回数券)」約1,436,936.36円と「内物販」約772,881.85円の合計で構成される(`parse_monthly_summary`で読み取り、いずれも日報Excel自身が計算した自己完結型の値。product-audit-spec.md §6参照)。

区分振替(§14)を適用した場合、店舗全体の実売合計は変わらないが、内訳(物販/施術・既存)の按分が変わる。守山8月では、8/17行8(5,750円)を物販から施術・回数券側へ振替た結果、次のようになる。

| 項目 | 区分振替前 | 区分振替後 |
|---|---|---|
| 店舗全体売上(実売合計) | 約2,209,818.21円 | 約2,209,818.21円(変更なし) |
| 物販売上 | 772,881.85円 | 767,131.85円 |
| 施術・既存売上(内回数券等) | 約1,436,936.36円 | 約1,442,686.36円 |

### 報告時のルール

以降、物販監査の結果を報告する際は、次の3つを明確に分けて表示する。

1. **店舗全体売上**(月報集計シート「実売（実績）」累計。区分振替の影響を受けない)
2. **物販売上**(本監査の対象範囲。区分振替後の値を正式値とする)
3. **施術・既存売上**(店舗全体売上 − 物販売上、または月報集計の「内回数券等」+区分振替額)

`run_product_audit.py`の出力(ログ・summary JSONの`store_overall_revenue`)は、この3区分を明示的に分けて出力する。`revenue_excl_tax.total`等、本監査エンジンが集計する金額は物販売上であり、店舗全体売上ではないことをコード・ログ双方で明示する。

## 18. 社内例外取引(2026-09-15確定)

### 背景

通常は販売しない備品・消耗品等を、店舗が仕入れた原価のまま社内購入する例外的な取引がある。例(守山8月8/24・とこちゃんベルト):小川麻菜が出産祝いとして贈るため、店舗が施術時に使用する備品として仕入れている「とこちゃんベルト」(通常お客様へ販売しない)を、原価のまま(4,950円)購入した。この商品は通常の商品マスター(`product_price_history.yaml`)には存在せず、原価マスターにも登録されていないが、これは「商品不明」「原価不明」という異常ではなく、そもそも通常販売品ではない備品を例外的に社内購入したという事実である。

### 確定方法・監査上の扱い

`accounting/config/stores/{store_id}/{year_month}/confirmed_exception_transactions.yaml`に、オーナー・スタッフ確認(レシート確認等)により確定した行(`store_id`・`year_month`・`date`・`row`・`product_name`・`purchaser_type_override`・`exception_type`・`note`)だけを明示登録する。`apply_confirmed_exception_transactions`(`product_audit.py`)が該当行に適用し、以下のように確定する。

- `classification`を「N(社内例外取引)」とし、severityを「正常」とする。「商品マスターに存在しない」「原価マスターに存在しない」ことを異常扱いしない。
- 商品名を確定した実際の商品名に更新し、`product_status`を「商品特定済み」とする。
- 購入者区分は、明示登録した`purchaser_type_override`をそのまま使う(スタッフ本人による購入であっても、通常の社割購入ではなく内部的な備品譲渡である場合は「社内購入」とする等、実態に応じて指定する)。
- 原価(`cost_excl_tax_total`)は税抜売上と同額とし、粗利益0円として確定する(店舗が仕入れた原価のまま譲渡したという事実を反映する)。

対象商品は、通常の商品マスター(`product_price_history.yaml`)には登録しない。今後、同じ商品が通常販売されるようになった場合は、その時点で商品マスターへの登録が必要になる。推測で追加せず、オーナー・スタッフ確認により確定した行だけを登録すること。

## 19. 現場確認に基づく個別確定(ステータス上書きの拡張・数量修正)(2026-09-15確定)

> **訂正(2026-09-15、§21参照):** 本節が当初の実例として挙げていた守山8月8/17
> 行6・行7への適用(行6単独をSへ上書き、行7の数量を2→1に修正)は、スタッフ回答の
> 再確認により誤りと判明し、いずれも撤回した。行6・行7・行8は1つの売上シェア
> グループであり、行7の数量「2」は正しい(誤りではない)。この節で説明する
> 仕組み(ステータス上書きの拡張・数量修正)自体は他のケースで引き続き有効だが、
> 8/17への適用は取り消し済み。8/17の正しい処理は§21(手動確定・売上シェアグループ)
> を参照。

### 背景

`detect_and_apply_shared_sales`(§11)による売上シェアの自動検出は、I列の明示記載と金額の一致という、日報Excel内で機械的に確認できる根拠だけを使う。しかし現場(スタッフ)への直接確認により、ファイル内に対応する行が見当たらない場合でも、価格異常や数量誤りといった事実が確定することがある(自動検出のモデルに当てはまらない売上シェアについては、§21の手動確定・売上シェアグループを使う)。

### 確定済みステータス上書きの拡張(§15の拡張)

`accounting/config/stores/{store_id}/{year_month}/confirmed_status_overrides.yaml`は、通常はseverityのみを「分類保留」に変更する(§15)。現場確認により価格異常自体が解消したと確定できたが、ファイル内に対応する行が見当たらず自動検出が使えないケースに限り、以下を追加で指定してclassification自体を上書きしてよい。

- `new_classification`:確定した区分(例:`S`)
- `new_price_status`:対応する価格監査ステータス
- `new_transaction_type`:対応する`transaction_type`
- `clear_flags`:追加の要確認フラグをクリアするか

ただし、売上シェアが複数行にまたがる場合(1つの「無」行が複数商品のシェアを受け止める等)は、行ごとに個別にこの上書きを使うのではなく、§21の手動確定・売上シェアグループを使うこと(グループ全体としての整合性を保つため)。

### 確定済み数量修正(`confirmed_quantity_corrections.yaml`)

数量そのものが日報の入力誤りだったと現場確認で確定した場合は、`accounting/config/stores/{store_id}/{year_month}/confirmed_quantity_corrections.yaml`に明示登録する。`apply_confirmed_quantity_corrections`(`product_audit.py`)が、監査前の生データ行の数量を修正してから`audit_transaction`を実行するため、価格一致判定・原価計算が正しい数量ベースで自動的に再計算される(元Excelは変更しない)。**数量の見た目が規定価格と合わない場合でも、それが「数量の入力誤り」なのか「売上シェアによる金額分割」なのかを取り違えないよう、現場確認の内容を注意深く確認してから、どちらの仕組みを使うか判断すること**(2026-09-15、守山8月8/17でこの取り違えが実際に発生し、訂正した)。

### 在庫帳突合への影響(既知の副作用)

数量修正・社内例外取引の適用により、在庫帳(店舗スタッフによる手入力の月間集計。§7参照)側の数量・原価が、日報の元の数量を前提に記録されたままになっている場合、在庫帳との突合(§9の在庫帳クロスチェック)で新たな差分が表面化することがある。これは監査ロジックの誤りではなく、在庫帳側がまだ確定済みの内容を反映していないことによる、説明可能な差分である。守山8月では、社内例外取引(とこちゃんベルト)の商品名変更により、在庫帳の「その他店販(標準税率)」ブロックに1個分の対応が取れなくなる差分が生じている。これは今回確定した事実から直接説明できる差分であり、別途の現場確認は不要だが、在庫帳自体を訂正するかどうかは会計AIの書き込み対象外のため、必要であれば別途店舗側で対応する。

推測で追加せず、現場確認により確定した行だけを登録すること。

## 20. 監査結果の観点別件数(2026-09-15確定)

守山8月の再監査結果を報告する際、単一の「要確認件数」だけでなく、次の6つの観点別件数を独立に集計して報告する(`run_product_audit.py`の`audit_status_counts`)。1取引が複数の観点に同時に該当しうるため、互いに排他的な分類ではなく、それぞれ独立に集計する。

| 観点 | 定義 |
|---|---|
| 価格異常 | classificationが「C(通常価格不一致)」または「D(スタッフ価格不一致)」の取引数 |
| 商品不明 | product_statusが「商品不明」の取引数 |
| 購入者不明 | purchaser_typeが「購入者不明」の取引数(顧客名が空欄で、確定済み連続購入ブロック§12の対象外のもの。それ自体は異常ではなく、原価・売上の確定を妨げない正常な区分の1つ) |
| 売上シェア未解決 | transaction_typeが「shared_sale_candidate」(3名以上シェア候補・未確定)または「unknown」(I列にシェア記載があるが対応する行が特定できないもの)の取引数 |
| 原価未確認 | cost_confirmedがFalseの取引数 |
| その他要確認 | severityが「要確認」で、かつ上記いずれの観点にも該当しない取引数(F・G・I等の残存分) |

「購入者不明」はそれ自体が異常ではなく、購入者区分(4分類)の1つとして正常に扱われることに注意する(§9・§10参照)。件数として報告するのは、現場確認の要否を判断する材料を提供するためであり、この件数がそのまま「要確認件数」を意味するわけではない。

## 21. 現場確認に基づく手動確定・売上シェアグループ(2026-09-15確定・§14/§19の訂正を含む)

### 経緯(訂正)

守山8月8/17の3行(行6:有機ほうじ茶パウダー270円、行7:プロテイン数量2・5,940円、行8:無・6,210円)について、当初は次のように誤って処理していた。

- 行7の数量「2」を、現場確認により「実際は1個の誤り」と解釈し、`confirmed_quantity_corrections.yaml`で数量を1へ補正していた。
- 行8の6,210円を、D・F・I列の記載から「施術(リンパ5回)側の売上」と解釈し、`confirmed_category_reclassifications.yaml`で物販から除外し、施術/既存側へ振替していた。
- 行6単独を、`confirmed_status_overrides.yaml`でS(売上シェア確定)へ上書きしていた。

スタッフ回答を再確認した結果、これらはいずれも誤りであったと判明した。正しくは、行6・行7・行8は**1つの売上シェアグループ**であり、行7の数量「2」は誤りではなく実際の販売数量どおり、行8は施術売上ではなく行6・行7の売上シェアのうち小川麻菜側の取り分(270円+5,940円=6,210円)である。上記3つの登録(数量修正・区分振替・単独でのステータス上書き)はすべて削除し、撤回した。

### 正しい解釈

- 有機ほうじ茶パウダー:実販売数量1個、通常価格540円。半額270円(行6、澄川真側)。
- ドクターセレン(プロテイン):実販売数量2個、通常価格11,880円(5,940円×2個)。半額5,940円(行7、澄川真側)。
- 商品売上合計:540円+11,880円=12,420円。
- 売上シェア配分:澄川真6,210円(行6+行7)、小川麻菜6,210円(行8)。270円+5,940円=6,210円で行8と完全一致する。

### 確定方法(自動検出の対象外のケース)

`detect_and_apply_shared_sales`(§11)の自動検出は、「1商品の商品あり行+その商品の無行(1〜2行)」という組み合わせしか扱えない。このケースは、1つの「無」行(行8)が**2つの異なる商品**(有機ほうじ茶パウダー・プロテイン)の売上シェアを同時に受け止めており、自動検出のモデルに当てはまらないため、自動では検出されない(検出されないこと自体は正しい挙動であり、バグではない)。

このような、現場確認により確定したが自動検出の対象外となるグループは、`accounting/config/stores/{store_id}/{year_month}/confirmed_manual_share_groups.yaml`に明示登録する。`apply_confirmed_manual_share_groups`(`product_audit.py`)は、登録されたグループに含まれる全行が実際に見つかった場合にのみ、`_apply_confirmed_share`(§11で使用する確定処理と同一ロジック)を適用する。

- 商品あり側の行(行6・行7)は、日報記載どおりの数量・原価をそのまま使う(二重計上しない)。行7の原価は、実販売数量2個分(3,950円/個×2個=7,900円)として計上する。
- 「無」側の行(行8)は、商品特定済み・原価0円・数量0として扱う(原価・数量の二重計上を防ぐ)。
- グループ全体の売上合計(12,420円)・classification(S)・severity(正常)は、自動検出のグループと同じ基準で確定する。

推測で追加せず、現場確認(スタッフ回答等)により確定したグループだけを登録すること。行が1つでも見つからない場合は、安全側に倒して何も適用しない。

### 財務数値への影響

上記の訂正により、8/17時点で誤って行っていた次の2つの調整はいずれも撤回される。

- 物販売上から5,750円を施術/既存側へ振替ていた処理 → 撤回(物販売上は772,881.85円に戻る)。
- プロテインの原価を1個分(3,950円)としていた計算 → 撤回(実販売数量2個分、7,900円に戻る)。

とこちゃんベルト(§18)の社内例外取引は今回の訂正と独立しており、変更しない(税抜原価4,500円を計上)。

## 22. 設定ファイルの3階層構成(2026-09-15確定)

### 背景

§11〜§21で追加した確定事実(売上シェア・区分振替・社内例外取引・購入者ブロック・ステータス上書き・数量修正)は、いずれも守山8月の実データから確認した事実であり、`accounting/config/`直下にフラットに置かれていた。この構成のまま他店舗(みよし等)を監査すると、守山固有の確定事実(例:8/17の売上シェア、とこちゃんベルト、辻明子の連続購入ブロック)が、無関係な店舗・月にも無条件で読み込まれてしまう。2026-09-15、みよし店8月の初回監査に着手する際にこの問題を認識し、設定ファイルを3階層に分離した。

### 3階層

1. **global**(`accounting/config/global/`):全店舗・全期間に共通して適用するルール。店舗名・年月をハードコードしない。
   - `product_price_history.yaml`:商品マスター(価格・原価の履歴)。マグネシウムの2026-08/2026-09価格切り替えを含む(§8)。
   - `staff_price_rules.yaml`:正式なスタッフ社割ルール。確定済み丸め差(`confirmed_rounding_tolerance_yen`、§16)を含む。
2. **store**(`accounting/config/stores/{store_id}/`):特定の店舗にだけ適用する設定。年月をまたいで有効(月が変わっても原則として引き継がれる)。
   - `staff_aliases.yaml`:その店舗のスタッフ・社内購入者の別名(alias)マスター(§10)。
3. **store×year_month**(`accounting/config/stores/{store_id}/{year_month}/`):特定店舗・特定年月にだけ適用する確定事実。
   - `confirmed_purchaser_blocks.yaml`(§12)
   - `confirmed_category_reclassifications.yaml`(§14)
   - `confirmed_status_overrides.yaml`(§15・§19)
   - `confirmed_quantity_corrections.yaml`(§19)
   - `confirmed_exception_transactions.yaml`(§18)
   - `confirmed_manual_share_groups.yaml`(§21)

`run_product_audit.py`の`default_config_paths(store_id, year_month)`が、この3階層の既定パスを毎回組み立てる。ファイルが存在しない場合(例:まだ確定事実が無い店舗・月)は、各`load_*`関数が空(`{}`・`[]`)として扱い、判定に一切影響しない。CLI引数で明示的にパスを指定すれば上書きできる。

### 判定基準(どの階層に置くか)

- **商品そのものの価格・原価・税率**(全店舗共通の商品マスター相当) → global。
- **その店舗のスタッフ・組織に関する事実**(名簿に無い名前の解決等)で、特定の月に限定されないもの → store。
- **特定の日報行に関する、現場確認済みの一回限りの事実**(売上シェア・例外取引・区分振替・特定の連続購入ブロック等) → store×year_month。
- 判断に迷う場合、または他店舗でも同じ内容か未確認の場合は、より狭い階層(store×year_month)に置き、確認が取れてから広い階層へ引き上げる(推測で広い階層に置かない)。

### みよし店8月での検証結果

みよし店8月の監査(守山固有の確定事実が0件のみよし用ディレクトリで実行)で、以下を確認した。

- マグネシウムの価格履歴汚染(§8と同一の事象)が、`_find_known_discrepancy`(§8)により自動的に「K(既知差異)」として解決された(店舗固有のコードや設定を追加せずに再現)。
- I列「売上シェア」の明示記載による2名シェア(8/1、マグネシウム)が、`detect_and_apply_shared_sales`(§11)により自動的に検出・確定された(店舗固有の設定を追加せずに再現)。
- 守山固有の確定事実(8/17の売上シェア、とこちゃんベルト、辻明子の連続購入ブロック等)は一切適用されなかった(該当ディレクトリにファイルが存在しないため)。

これにより、監査ロジックの汎用部分(価格履歴・既知差異・売上シェア自動検出・在庫帳突合等)が店舗をまたいで正しく再利用できることを確認した。
